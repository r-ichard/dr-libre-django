# Plan: `make audit` checks the locked packages for known vulnerabilities (26c item 13)

Slice: item 13 of task 26c only. Nothing else of `doc/backlog/26c-gates-that-hold.md`.

## Focal point

`make audit` runs **pip-audit 2.10.1** over the packages pinned in `uv.lock` and exits 1 on any
known vulnerability. It is not part of `make test`.

## Tool, version, why

- **pip-audit 2.10.1**, the PyPA tool. 2.10.1 is the latest PyPI release on 2026-11-23 (checked
  against the PyPI JSON API). Pinned exactly in the `dev` dependency group, as pytest, ruff, mypy
  and mutmut already are.
- **Why pip-audit:** it is maintained by PyPA, reads the Python advisory data, and audits a
  requirements file, so it checks what `uv.lock` pins and not whatever is installed.
- **Why `--require-hashes` with the default `pypi` service:** pip-audit warns that with
  `--service osv`, `--require-hashes` only checks that hashes exist. With `pypi` it checks that
  they are valid. The export therefore keeps the hashes `uv export` writes.
- **Not used:** `pip-audit --locked`. In 2.10.1 it reports "no lockfiles found" for this
  repository's `uv.lock`, so the export step stays. Other scanners were not evaluated in depth.
- **Probe (scratch, outside the repo, 2026-11-23):** `uv export --locked` gave 40 packages;
  pip-audit with `--require-hashes --disable-pip` on that file printed "No known vulnerabilities
  found", exit 0. A scratch file pinning `django==3.2.0` exited 1 with four advisories.

## No new product runtime dependency

`pip-audit` goes only into `[dependency-groups] dev`. `[project] dependencies` is unchanged and
no product code imports it. The Dockerfile runs `uv sync --locked`, which already includes the dev
group for pytest, so the dev image gets the tool too. The product runtime does not change.

## Blocks, in file order

1. `pyproject.toml`, `dev` group: add `"pip-audit==2.10.1",` after `"hypothesis==6.170.17",`.
   `uv.lock` is regenerated by the same `uv add --dev pip-audit==2.10.1`; the diff must only add
   pip-audit's own pins.
2. `scripts/audit.sh` (new, POSIX sh, about 10 lines). One `mktemp -d` work directory, removed on
   exit, holds the requirements file and the pip-audit cache. `set -eu`. Step one:
   `uv export --locked --no-emit-project --format requirements-txt` into the work directory;
   `--locked` fails on a stale lock rather than auditing an old file. Step two:
   `uv run pip-audit --require-hashes --disable-pip -r <file> --cache-dir <work>/cache`. Its exit
   status is the script's. `--no-deps` is not needed: with `--require-hashes` pip-audit calls it
   redundant. The cache is temporary so each run asks for fresh advisories and does not depend on
   `~/.cache`, which the sandbox refused for pip-audit during the probe.
3. `scripts/test_audit.py` (new). It runs `scripts/audit.sh` with a stub `uv` first on `PATH`.
   The stub appends its arguments to a log file and exits with a code from an environment
   variable. No network.
4. `Makefile`: add `audit` to `.PHONY`; target `audit:` with recipe `sh scripts/audit.sh` and one
   comment line above: not part of `make test`, queries a vulnerability service (§11).
5. `README.md`: one line after the intro paragraph (line 3): when to run `make audit`
   (before a hand-over and after any change to `uv.lock`); it needs network and is not part of
   `make test`.
6. `doc/handover.md`, the fresh-clone list (lines 28 to 29): add `make audit`. CLAUDE.md says
   recipes for the next carrier are kept current in the commit that changes them. Droppable if the
   orchestrator wants the diff smaller.

**Not touched:** `drlibre-specs.md`, `doc/backlog/*`, product code, migrations, `Dockerfile`,
`compose.yaml`, the other gates, `doc/adr/`.

## Failing tests first (`scripts/test_audit.py`)

Expected values come from the task: pip-audit's failure on a vulnerability passes through; a clean
audit succeeds; a failed export never reads as a clean audit.

1. `returns_failure_when_pip_audit_reports_a_vulnerability`: stub audit exits 1, script exit is 1.
2. `returns_success_when_pip_audit_reports_no_vulnerability`: stub audit exits 0, script exit is 0.
3. `returns_export_failure_without_auditing_when_uv_export_fails`: stub export exits 2, script
   exit is 2, and the log has no `run` line.
4. `returns_hashed_locked_requirements_to_pip_audit_when_run`: log shows `export --locked` and
   `run pip-audit --require-hashes`.

Red for the right reason: before `scripts/audit.sh` exists, tests 1 to 3 fail on the exact codes
(127 is not 1, 0 or 2) and test 4 fails on the missing log lines. Exact code assertions keep a
missing script from passing by accident. Guard proof (later stage): break the script once, by
dropping `--require-hashes` and then by ignoring pip-audit's status; tests 4 and 1 must fail.

## Risks

- **Unreachable service may pass.** If pip-audit skips packages it cannot check and exits 0, `make
  audit` would read as clean with no network. The host check above decides it. If it passes
  silently, the script adds a check that a "packages audited" count is non-zero, or pip-audit's
  output format is changed.
- **Sandbox cache.** pip-audit's default cache under `/root/.cache` was refused in the probe
  ("writable by another user"). The temporary cache directory avoids it; `uv` itself worked.
- **Advisory data changes.** A later run may fail on an advisory with no code change. That is the
  intent of the target; the fix is a pin bump or a reviewed decision, not a suppression in this
  change.
