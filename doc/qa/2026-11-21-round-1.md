## #10 P1: Password sign-in page answers 500 for a malformed email address

### Summary
The password sign-in page answers HTTP 500 when the email field is not a valid address (for example `a@b`, which a browser's `type=email` accepts). The JSON login route answers 400 `invalid_input` for the same value.

### Steps to reproduce
Fresh `docker compose up --wait` with the demo seed:
```
B=http://127.0.0.1:8000; J=$(mktemp)
T=$(curl -s -c $J $B/sign-in | grep -o 'csrfmiddlewaretoken" value="[^"]*' | head -1 | cut -d'"' -f3)
curl -s -o /dev/null -w '%{http_code}\n' -b $J -H "Origin: $B" \
  --data-urlencode "csrfmiddlewaretoken=$T" --data-urlencode "email=a@b" -d password=x $B/sign-in
curl -s -w ' %{http_code}\n' -H 'Content-Type: application/json' -d '{"email":"a@b","password":"x"}' $B/api/v1/auth/login
```
Also 500: `not-an-email`, `a@b@c`. In a browser: type `a@b` and any password on `/sign-in`, press "Sign in".

### Observed
Page: 500 "Something went wrong". The log has `unexpected error` with `ValueError` for each request. The API route answers 400 with a field message for `email`.

### Expected
Section 4: "Expected failures are results, not crashes". The page shows a validation message (or the generic failed-sign-in message), status 400 or 200, never 500. Section 12.1 covers sign-in.

### Evidence
`scratch/qa/server.log`: `"message": "unexpected error"`, `"type": "ValueError"`, e.g. correlation id `edafe78ac84e4854a7b8d0fedfbb9b33`. Likely cause, not verified in code: `email_domain()` in `scheduling/domain/audit_metadata.py` raises on a malformed address when the page form calls it before validating. The email-link form on `/sign-in/email-link` answers 400 for the same values.

## #12 P1: Slots and booking answer 500 for dates at the calendar edge (year 9999 or 0001)

### Summary
`GET /api/v1/slots` and `POST /api/v1/appointments` answer 500 when a date sits at the edge of the calendar (year 9999 or 0001). Slots is reachable without signing in.

### Steps to reproduce
Fresh `docker compose up` with the demo seed; `CONS` is the id of the cardiology consult type, `CA` the `clinician@` profile id, patient signed in as the demo patient (cookie jar `patient.jar`).
```
curl -s "$B/slots?appointment_type_id=$CONS&from=9999-12-31T00:00:00Z&to=9999-12-31T23:00:00-05:00"
curl -s "$B/slots?appointment_type_id=$CONS&from=0001-01-01T00:00:00Z&to=0001-01-02T00:00:00Z"
curl -s -b patient.jar -X POST $B/appointments -H 'content-type: application/json' -H 'Origin: http://127.0.0.1:8000' -d "{\"appointment_type_id\":\"$CONS\",\"clinician_id\":\"$CA\",\"starts_at\":\"9999-12-31T23:59:59Z\"}"
curl -s -b patient.jar -X POST $B/appointments -H 'content-type: application/json' -H 'Origin: http://127.0.0.1:8000' -d "{\"appointment_type_id\":\"$CONS\",\"clinician_id\":\"$CA\",\"starts_at\":\"0001-01-01T00:00:00Z\"}"
```
`POST /api/v1/booking/holds` with `starts_at` 9999-12-31T23:59:59Z failed the same way in the first run; I could not repeat it in the verify run because the hold endpoint was already rate limited (429), so treat the hold case as likely, not re-confirmed.

### Observed
HTTP 500 `internal_error` for all four. Server log: `OverflowError` in `scheduling/use_cases/placement_checks.py` (`slot_of`, start plus duration) and in the slot query. Correlation ids from the verify run: 04fc0dc1cbe74d3ab47fd75ace00bbb3, f9452d7f698f41bf9aaaad2d6c19d6c0, 27f1a378ad50444587d0887c2b79e03f, 3bbe926b172d43f18cc98d32041d8e03.

### Expected
Section 4: input is validated at every boundary and expected failures are results; no request answers 500. A date out of range gives 400 `invalid_input` (or an empty slot list / `outside_availability`).

### Evidence
Correlation ids above, in `scratch/qa/server.log`.

## #18 P1: Public routes answer 500 for too many query fields, huge or deeply nested bodies

### Summary
Public routes answer 500 `internal_error` for a request with too many query or form fields, a very large JSON body or deeply nested JSON. Related to #14, which reports the body cases only on `POST /appointments`; these routes need no session and the query-string case is new.

### Steps to reproduce
Fresh `docker compose up --wait`, no session, `B=http://127.0.0.1:8000/api/v1`.
```
curl -i "$B/search/providers?$(python3 -c 'print("&".join("a%d=1"%i for i in range(1500)))')"
python3 -c 'print("["*100000)' > deep.json
for p in booking/holds auth/link auth/login; do curl -i -X POST $B/$p -H 'content-type: application/json' --data-binary @deep.json; done
python3 -c 'print("{\"a\":\""+"x"*20000000+"\"}")' > huge.json
curl -i -X POST $B/booking/holds -H 'content-type: application/json' --data-binary @huge.json
```
(900 query parameters answer 200; 1500 answer 500.)

### Observed
Every command answers 500 `{"error":{"code":"internal_error",...}}`. `server.log` shows `TooManyFieldsSent` (query string), `RecursionError` (nested) and `RequestDataTooBig` (large) for these correlation ids. The same many-parameter query on the HTML page `/` answers 400 correctly.

### Expected
Section 4: expected failures are results in the failure contract, never a crash. Answer 400 `invalid_input` (or 413 for a large body). For the search query string, ignore the excess or answer 400.

### Evidence
`scratch/qa/server.log` lines with `"status": 500` on `api/v1/search/providers`, `api/v1/booking/holds`, `api/v1/auth/link`, `api/v1/auth/login`.

## #11 P2: Confirmation page and calendar file answer 404 instead of 403 for another patient's appointment

### Summary
The booking confirmation page and the calendar file answer 404 for an appointment that exists but belongs to another patient. The specification says that case answers forbidden.

### Steps to reproduce
Fresh `docker compose up --wait` with the demo seed. Sign in as `patient@example.test` (password from `.env.example`), then request an appointment of another patient:
```
B=http://127.0.0.1:8000; J=$(mktemp)
curl -s -c $J -H 'Content-Type: application/json' -d '{"email":"patient@example.test","password":"<DEMO_PASSWORD>"}' $B/api/v1/auth/login
### OTHER = id of an appointment of passwordless@example.test (list as admin@example.test via GET /api/v1/appointments)
curl -s -o /dev/null -w '%{http_code}\n' -b $J $B/appointments/$OTHER/confirmation
curl -s -o /dev/null -w '%{http_code}\n' -b $J $B/appointments/$OTHER/calendar.ics
curl -s -o /dev/null -w '%{http_code}\n' -b $J $B/patient/appointments/$OTHER/cancel
```

### Observed
`confirmation` 404, `calendar.ics` 404 (same as for a nonexistent id). `/patient/appointments/<id>/cancel` answers 403 for the same id and 404 for a missing one. No data leaks.

### Expected
Section 12.3: "A missing record gives `not_found`; a record that exists but belongs to someone else gives `forbidden`." Both routes answer 403 for someone else's appointment and 404 for a missing one, like the portal pages.

### Evidence
`scheduling/views/pages/booking_confirmation.py` (`own_appointment`) raises `Http404` whenever `appointment_for_patient` returns `None`, so it cannot tell the two cases apart.
