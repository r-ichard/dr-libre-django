### #45 P2: Booking reason accepts a number and stores it as text

#### Summary
`POST /api/v1/appointments` accepts a JSON number for `reason` and stores it as text. Other wrong types (boolean, list, object) are refused with `invalid_input`, so the boundary is inconsistent.

#### Steps to reproduce
Demo seed, `docker compose up`. Sign in as the demo patient (`patient@example.test`, `DEMO_PASSWORD` from `.env.example`) with `POST /api/v1/auth/login`, keeping the cookie in `jar`. Take a provider id, appointment type id and a free start from `GET /api/v1/search/providers` or `GET /api/v1/slots`.
```
curl -s -b jar -X POST http://127.0.0.1:8000/api/v1/appointments \
  -H 'content-type: application/json' -H 'origin: http://127.0.0.1:8000' \
  -d '{"appointment_type_id":"<type>","clinician_id":"<clinician>","starts_at":"<free start, Z>","reason":12345}'
```
Repeat with `"reason":true`, `["a"]`, `{"a":1}` for comparison.

#### Observed
`201`, body `"reason":"12345"`. The boolean, list and object variants answer 400 `invalid_input` with `{"field":"reason","message":"Not a valid string."}`.

#### Expected
Section 4: "Every input is validated"; a number is not a string and should answer 400 `invalid_input` like the other wrong types. #### Evidence
Reproduced by the verifying reader on the running stack: 201 with `"reason":"12345"` (appointment `01a2032b-9675-741b-aa9c-4a745063af74` in that run), 400 for the three other types. Impact is low: no data leaves the system and the stored value is harmless.
